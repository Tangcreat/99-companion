## 一、跑起来

1. 双击 `run.bat`（或在目录里 `python server.py`）
2. 浏览器打开 http://127.0.0.1:8787
3. 右上「设置」填 Base URL、API Key、模型名 → 点「测试连接」

## 二、导入角色

支持三种卡：

| 格式 | 说明 |
|---|---|
| **Tavern Card V2** | `{spec:"chara_card_v2", spec_version:"2.0", data:{...}}`，SillyTavern / RisuAI 生态的通用格式 |
| **PNG 内嵌卡** | 把 JSON 塞在 PNG 的 `tEXt` chunk（keyword=`chara`），直接把图拖进来即可 |
| **V1 裸卡** | `{name, description, personality, first_mes, ...}` |

校验规则：人设必须 ≥ 200 字（要能写出说话方式、性格、边界，太短的卡跑起来一定像个客服机器人）。

示例卡在 `sample-cards/shen-zhixia.card.json`，可以直接导入看效果。

### 卡片字段

```jsonc
{
  "spec": "chara_card_v2", "spec_version": "2.0",
  "data": {
    "name": "沈知夏",                    // 必填
    "description": "她是谁",             // V2 字段，会拼进人格
    "personality": "性格",
    "scenario": "处境",
    "first_mes": "第一句话",
    "mes_example": "对话样本",           // 强烈建议写，能大幅提升语气像不像
    "interests": ["旧书", "雨声"],        // 她自己的兴趣，用于主动搭话
    "tags": ["温和", "慢热"],
    "series": "",                        // 作品来源，原创留空

    // ↓ 本项目扩展（可选）
    "schedule": { "sleep": "00:40", "wake": "08:30",
                  "label": "明天要早起开店" },   // 不填则按名字自动派生
    "traits":   { "enthusiasm": 45, "affection": 55 },
    "extensions": { "accent": "#b9a58c" }        // 主题色
  }
}
```

### 目录形态

导入后每个角色一个目录，**人设是 Markdown，你可以直接手改**：

```
characters/沈知夏/
├── card.json     声明（名字/兴趣/主题色/作息）
├── persona.md    人格正文 ← 改这个最有效，改完刷新页面就生效
├── avatar.png    256×256（可选）
└── state.json    运行时标记
```

`persona.md` 是权威副本：它和 `card.json` 里的 `persona_md` 不一致时，以 `persona.md` 为准。

## 三、它和原版怎么对应

| 能力 | 原版做法 | 这里 |
|---|---|---|
| 双通道推理 | analyze（JSON）+ express（生成） | 同，`core/think.py` |
| 三层记忆 | 画像 / 情节 / 情绪，SQLite | 同，`core/db.py` + `core/memory.py` |
| 记忆版本链 | `root_id/previous_id/version/superseded_at` | 同（记忆可被"修正"而非覆盖） |
| 向量召回 | 本地字符 n-gram 哈希 256 维 | 同，`embed()` 一个函数，可整体换真 embedding |
| 事实三态 | candidate/confirmed/conflict | 同，只有 confirmed 进人格 |
| 拟真参数 | 热情/好感 → 频率与延迟 | 同，`core/traits.py`（真实聊天分位标定） |
| 作息 | 未配置按名字派生 | 同，`core/schedule.py` |
| 角色卡 | 私有 spec 1.0 | **Tavern V2 兼容** + 扩展字段 |
| 局域网同步 | 整包备份 + SHA256 | 未实现（自用单机不需要） |
| QQ/OneBot 通道 | 占后端约 1/4 代码 | 未实现（桌面直聊不需要） |

## 四、代码结构

```
server.py              HTTP 服务 + 路由 + 聊天主流程（标准库）
core/db.py             SQLite schema（记忆版本链、事实三态、状态）
core/memory.py         embed / cosine / recall / revise（版本链）
core/cards.py          角色卡解析（V2/V1/PNG）、头像规范化
core/traits.py         热情好感 → 主动频率与回复延迟
core/schedule.py       作息派生与睡眠判定
core/think.py          双通道 prompt 组装
core/llm.py            OpenAI 兼容客户端
web/index.html         单页界面（无构建）
characters/            你的角色（导入后生成）
data/companion.db      所有记忆与对话
```

## 五、已知限制

- **没有主动性后台循环**。`traits.proactive_interval_minutes()` 已经算好间隔，但没接调度器——现在只有你说话它才回。要开主动消息，在 `server.py` 里加个线程按间隔调 `thinker.has_something_to_say()`，先问"真的有话说吗"再发。
- **没有流式输出**。回复整段返回。要流式得改 `llm.py` 加 `stream=True` 并按 SSE 推。
- **群聊/多角色同场**没做（原版占 118KB 代码，自用价值低）。
- **记忆检索**是词袋哈希，同义改写召回不到。要准就换 embedding——只改 `memory.embed()` 一个函数。

## 关系阶段（好感度分级）

好感不只是"频率倍率"，它决定**能聊到哪一层**。每一档都写死了可以做什么、还不能做什么：

| 好感 | 阶段 | 分寸 |
|---|---|---|
| 0–29 | 生疏 | 客气、有分寸，不碰感情话题 |
| 30–54 | 熟识 | 聊日常与喜好，试探用玩笑带过 |
| 55–74 | 亲近 | 可以说在意、说想念，但不明说心意 |
| 75–89 | 很亲近 | 有偏心和暧昧的试探，半真半假地撩 |
| 90–100 | 暧昧 | 可以明着撩、撒娇、吃醋 |

两条线始终守住：不写露骨性描写；不写「只有我能救你」这类不健康绑定。

好感随互动质量缓慢上涨（一次最多 +2），也可以在角色面板里手动拉。

## 群聊

左栏顶部那个「+人」按钮会按**同场关系**自动建群——数据来自每个角色档案里的
「同场角色（按共同出场关卡数）」表，那是官方剧情里他们一起出现过多少场。
维尔汀的群自然是十四行诗、红弩箭、星锑。

群里每次会有 1~2 个角色接话，按与上一位发言者的同场强度加权挑选。

## 三层上下文（v1.1 重构）

角色的「知道什么」拆成三层，各走各的检索，互不挤占：

| 层 | 存在哪 | 什么时候进 prompt |
|---|---|---|
| **共用世界观** | `data/world.json`（22 条） | 只在用户提到相关词时，最多 2 条 |
| **她的一生** | `characters/<角色>/lore.json` 的 `history` 条目 | 问「你的故事/过去/以前」时走时间线；否则按关键词 |
| **和你聊出来的** | SQLite `memories` | 每轮向量召回 top-6 |

### 为什么要有「时间线模式」

只靠关键词命中，「给我讲讲你的故事」这种泛问永远碰不到「阿派朗岛」「平凡结」
这种具体触发词，角色只能回答「我没有故事可讲」——这是实测出现过的真实故障。

所以 `core/lore.py` 里加了一层意图判断：

```python
is_past_intent("给我讲讲你的故事吧")   # True
is_past_intent("你最喜欢做的事是什么") # False
```

命中后不再逐条碰运气，而是把 `history` 按章节号排序整条取出来，
以「1. 2. 3.」的编号形式注入，模型自然理解成先后发生的一条人生线。

同时 prompt 里写死了硬约束：**除非确实一条经历都没有，否则不许说自己「没有故事」
「不是从某一天开始存在的」**。想不起细节可以说「记不太清了」，但不能否认有过去。

## v1.6：升级后功能没生效的根因

现象：APK 里明明有新界面，装上却只有第一版的界面——剧情回顾、表情面板、
聊天菜单、我的资料全都看不到。

根因在 `MainActivity.copyAssetDir` 的第一行：

```kotlin
if (dest.exists()) return      // 目录已存在就整个跳过
```

首次安装时 `assets/web` 被复制到 `filesDir/web`，之后每次升级都走了这个 return，
**前端文件永远停在第一次装的那个版本**。角色数据因为有单独的 versionCode 判断会刷新，
所以「角色是新的、界面是旧的」——这个组合很容易被误判成「功能没做」。

修法：`syncWebAssets()` 每次启动强制覆盖 `web/`，用 `.web_version` 标记记录已刷版本；
同时 `loadUrl` 带上 `?v=<versionCode>` 绕开 WebView 对 HTML 的缓存。

另外把 `android_entry.py` 从被 gitignore 的生成目录挪回项目根，由
`tools/sync_android.py` 输出——之前它不在版本库里，换机器就会丢。

## v1.6：角色把中午说成凌晨

现象：中午 12 点发消息，角色回「现在是 1 点钟」。

两个原因，第一个是硬 bug：

**① 午睡被当成深夜。** `describe_phase` 里 `is_asleep()` 为真时统一返回
「现在是深夜/休息时间，你已经睡下了」。122 个角色里有 32 个带午睡窗口
（12:00~14:00 区间），任何人在午睡时段找她们，prompt 里写的都是「深夜」——
模型照着「深夜」答，自然答成凌晨一点。现在午睡和夜眠分开描述：
午睡时说「你在午睡（平时 12:18~12:48），刚被消息吵醒」。

**② 时间格式要模型自己换算。** 原来注入的是 `2026-11-04 12:20（三）`，
`（三）` 既可能是星期三也可能被读成 3 点，24 小时制还要换算。现在直接给口语：

```
现在是 2026 年 11 月 4 日 星期三，中午 12 点 20 分（24 小时制 12:20）
```

并加了一条硬规则：对方问几点／几号／星期几，就照这条答，别推算、别换算。

**③ 时区兜底。** Android 上 Chaquopy 的 Python 不一定拿得到设备时区。
新增 `core/clock.py`，由 Kotlin 侧把 `TimeZone.getDefault().getOffset()` 传进来，
`now()` 统一从这里取。设备时区偏移也进了诊断页，一眼能看出是不是漂了。

诊断页现在最上面有一张「时间」卡：本机时间、时区、来源（手机传入／系统默认）、版本号。
「我的」页副标题也会显示 `手机版 v1.6`，方便确认装的到底是不是新版。

## 添加角色：草稿 → 编辑/试聊 → 正式入住

不再是「填个名字直接建卡」。流程分三段：

1. **拿草稿**：联网生成草稿 / 导入 JSON 角色卡 / 使用预设，三选一
2. **检查与试聊**：改人设（作品、别名、简介、兴趣、完整 Markdown），
   随时在「创建前试聊」里跟她说两句——**最多 24 条临时上下文，不写记忆、不建正式角色**
3. **确认添加**：选好头像（拖动+缩放裁剪成 256×256）后点「确认添加角色」，才真正建卡

草稿有 `revision` 乐观锁：每次保存 +1，版本对不上会提示「草稿已被修改」，
防止两个窗口互相覆盖。保存/试聊/提交都强制校验 revision 为整数。

预设是本地 JSON（`web/character-presets.js`）：空白模板 + 青梅竹马 / 温柔学姐 /
可靠搭档 / 犀利编辑。可以「下载所选 JSON」改完再导入，也可以直接「使用预设」，
**全程不请求模型**。

接口：`POST /api/character-drafts/generate|import|chat|commit`、
`PATCH /api/character-drafts`、`GET /api/character-drafts`。

## 角色性别与人称（v1.7）

**问题**：生成「李白」的人设却通篇用「她」。

**原因**：`core/persona_builder.py` 的生成 prompt 里有一条写死的硬性要求
`- 写"她"而不是"这个角色"`。这条是最早为女性角色定的，结果所有角色都被写成女性。

**修法**：

1. 生成时让模型先判断性别，输出 `gender: male / female / other`，人称跟随它
   （李白 → 他，林黛玉 → 她，拿不准 → TA）
2. `InternalCard` 与草稿都增加 `gender` 字段，`card.json` 里可查
3. 添加角色弹窗新增「性别」下拉：自动判断 / 男性 / 女性 / 不确定，可手动覆盖模型的判断
4. 旧接口兜底：调用方没给 gender 时，按人设里「他/她」的出现次数粗判（判据保守，两侧接近就返回 other）

小标题也从「她是谁」改成「身份」，不再是女性预设。

## 启动端口判定（v1.7）

**问题**：进程被强杀后，Windows 偶尔留下处于 LISTENING 的僵尸 socket——
能 connect 通但没人 accept。旧逻辑据此判断「已有一份在运行」，只开窗口不启服务，用户看到白屏。

**修法**：`launcher.py` 改成先做健康检查（拉 `/api/characters`），
只有真返回 200 才认为实例在跑；否则用 `bind` 判断端口是否可用，
不可用就自动向后找端口（8787→8788…），并把端口写进 `STARLIT_PORT` 供 server 使用。
